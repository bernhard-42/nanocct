## 8. Open questions and next steps

### Open

- **8.3** **Clang's builtin headers when only the pip `libclang` wheel is available.** The parse needs clang's own resource-dir headers — measured 2026-09-23 on a representative OCCT set (`BRepPrimAPI_MakeBox`, `TopoDS_Shape`, `Standard_Transient`, `NCollection_Array1`, `math_Vector`): **exactly 23 files, 116 KB** (`stddef.h`, `stdarg.h`, `float.h`, `limits.h`, `stdint.h`, `inttypes.h`, Apple's `ptrcheck.h` and the `__stddef_*`/`__stdarg_*`/`__float_*` fragments clang 18+ splits them into). `parse.py` gets them from `clang -print-resource-dir` and passes `-resource-dir`; the pip `libclang` wheel ships **only** `libclang.dylib` (75 MB, no headers at all), so without a `clang` binary on `PATH` every parse dies on the first `#include <stddef.h>`.
    - **It cannot make the generator host-free, and that is not the goal.** The same parse pulls **1 050 headers** from the macOS SDK and libc++, because OCCT's headers include `<iostream>`, `<memory>`, `<vector>`; Linux needs libstdc++ from a host gcc; Windows needs the MSVC STL and the Windows SDK — **8 installed OCCT headers include `windows.h`** and 32 carry `_WIN32`/`WNT_` branches. The generator parses real C++ and therefore always needs the platform's toolchain (8.2).
    - **The case it does address is Windows**, where MSVC is the toolchain and a `clang` binary is genuinely often absent while the STL and SDK are present. There the wheel is the only libclang, and its compiled-in resource-dir path does not exist on the machine.
    - **If taken, follow the FreeType/RapidJSON precedent (8.13): a `deps/` fetch script with a pinned version and a checksum, not 23 files copied into git** — and pin them to the *wheel's* clang version (the wheel is 18.1.1 here, the Xcode clang 21; the mismatch is invisible today only because the system libclang wins). Not decided; nothing depends on it until 8.2.
- **8.10** **Pixel-buffer view as a Python addition (2c)** — expose `Image_PixMap`'s data (`Data()`/`ChangeData()`/`Row()` are raw pointers, 2d) as a buffer-protocol/`nb::ndarray` view of shape `(height, width, channels)` with `keep_alive`, writable for `ChangeData()`, so `numpy.asarray(px)` / `PIL.Image.fromarray(...)` and the reverse (a Pillow-loaded PNG pushed into a pixmap) work without a per-pixel loop. Today the per-pixel route works: `PixelColor()`/`SetPixelColor()` measured at ~0.3 µs/pixel (512×512 RGBA in 0.08 s; 1080p ≈ 0.6 s), or `Save("x.ppm")` + Pillow. Same mechanism for the other byte buffers (`NCollection_Buffer`, `FSD_Base64`, glTF/STL buffers — 8a "revisited with DataExchange"). First check: whether `nb::ndarray` works under the stable ABI (*unverified*). Pixmap row order (`IsTopDown()`) must be documented with it.

- **8.11** **Hash/eq contract for classes with `operator==` but no `std::hash`** — 57 bound classes (`Bnd_Range`, `NCollection_Vec2/3/4<float>`, `Graphic3d_MaterialAspect`, the `NCollection_ForwardRangeIterator` instantiations, …) have a value `__eq__` and nanobind's identity `__hash__`: `a == b` with `hash(a) != hash(b)`, so a dict/set lookup by an equal value fails silently. Python's own rule is `__hash__ = None` for such classes (unhashable). Options: (a) emit `cls.attr("__hash__") = nb::none()` for every class with `__eq__` and no `std::hash` — correct, but such objects stop being dict keys by identity; (b) leave as is (OCP does the same); (c) a value hash from the fields — not derivable in general. **Decided 2026-09-22: leave as is (b) for now — to be revisited** (user: "Leave hash as is, but add to Design.md to revisit this decision"); the recommendation on the table is (a). Counted 2026-09-22 (`__eq__` in `__dict__`, no own `__hash__`).

- **8.16** **The map set operations are bound only under the spelling OCCT deprecates.** `NCollection_Map` and `NCollection_PackedMap` still carry `Union`/`Unite`/`Intersection`/`Intersect`/`Subtraction`/`Subtract`/`Difference`/`Differ` as members, and the hand-written binder binds them (`src/cpp/common/nanoocp_ncollection.h:330`), so `NCollection_Map[int]().Union(a, b)` and `TColStd_PackedMapOfInteger().Unite(other)` work today. But in OCCT 8.0.1 those members are inline forwarders marked `Standard_DEPRECATED("This method will be removed right after 7.9. release. Use methods from NCollection_MapAlgo.hxx instead.")` — `NCollection_Map::Union` calls `NCollection_MapAlgo::Union<NCollection_Map>(*this, theLeft, theRight)`, and `NCollection_PackedMap.hxx` carries 12 such markers pointing at `NCollection_PackedMapAlgo`. The successors live in the namespaces `NCollection_MapAlgo` and `NCollection_PackedMapAlgo`, which nanoOCP does **not** expose: both are template-only, so they contribute no bound member and `ir.namespaces` never creates a module for them (`generator/parse.py:1876`). The fix is in the binder, not the generator — call `NCollection_MapAlgo::Union<M>(self, a, b)` instead of `self.Union(a, b)` for each of the eight operations, which keeps the Python spelling identical while dropping the deprecated call. Worth doing before OCCT removes the members, since that removal would break the binder's compile rather than degrade quietly. Found 2026-09-24 while reconciling nanoOCP's modules against the namespace list in the OCCT reference documentation: of its 39 namespaces, 15 are package modules (a namespace named like its package *is* the package), 12 are submodules of the nine package directories, 2 are in `overrides.toml [skip] namespaces` (`std`, `step`), and the remaining 10 are absent — `IVtkTools` because TKIVtk is out of scope, and the other nine (`occ`, `opencascade`, `BRepGraph_IteratorDetail`, `Graphic3d_TransformUtils`, `NCollection_ForwardRangeDetail`, `NCollection_ItemsView`, `NCollection_MapAlgo`, `NCollection_PackedMapAlgo`, `OpenGl_HashMapInitializer`) because they contain nothing but templates. Only the two `*MapAlgo` ones have a Python-visible consequence.

### Roadmap

- **8.5** **Python-side subclassing of abstract OCCT interfaces (nanobind trampolines)** — `math_Function`/`math_MultipleVarFunction` (the classic `math_BFGS`, `math_NewtonMinimum`, `math_FunctionRoot` are bound but need a Python-defined function), `Adaptor3d_Curve`/`Adaptor3d_Surface`, `Message_Printer`. This is the answer to the 249 functor-template lines of the report (`MathOpt::BFGS<F>` & co. need a C++ functor type and stay out, decision 2026-09-21): one rule "an abstract class with public virtuals gets a trampoline" makes the classic algorithms usable from Python. A subsystem of its own (trampolines, GIL, lifetime of Python-held objects referenced from C++); not needed by build123d; after Phase 1.

- **8.6** **An OCP compatibility shim.** A generated package that mimics cadquery-ocp's API on top of nanoOCP: `_s` aliases for every static method, `OCP.collections`-style container names, the `TopoDS` class-like object, flat exceptions — generated from the manifest, explicitly non-1:1, in its own distribution. Stretch goal: name the package `OCP` so that build123d's (and CadQuery's) own test suites run against nanoOCP **without any change** — the strongest possible integration test for nanoOCP, and a migration path for those projects. Not before Phase 1 and DataExchange are generated (the shim is only as complete as the bindings under it). The rename table in 8b is the specification's starting point.

- **8.6a** **A viewer** (user: "OpenGL would be good at some point", 2026-09-22). **Two of the three steps are done:** OCCT is built with `USE_OPENGL=ON` (3.1) and `TKOpenGl` is generated — `OpenGl_GraphicDriver` gives `V3d_Viewer` a real driver, so display and camera work headlessly. **Rendering works on macOS today** (2026-09-22): `Cocoa_Window(title, x, y, w, h)` creates its own `NSWindow` and `ToPixMap` returns the rendered image, so screenshots need nothing further — except an `NSApplication`, for which `tkinter.Tk()` serves. **`examples/window.py` is the working combination**: a visible 900×700 OCCT window with a steel-blue box, redrawn from tkinter's timer (`root.after(16, tick)` + `mainloop()`), which is what pumps the Cocoa event queue — a bare `while True: Redraw()` loop paints nothing and macOS marks the window unresponsive. `V3d_View` has no `View_Axo()` in OCCT 8; the axonometric view is `SetProj(V3d_XposYnegZpos)`. **Linux works too since 2026-09-24**: with `USE_XLIB=ON` (3.1) `Xw_Window(connection, title, x, y, w, h)` is bound and the driver, `AIS_InteractiveContext.Display`, `FitAll` and `Redraw` all run under `xvfb-run` (llvmpipe) — the three `test_TKOpenGl` driver tests pass there. **What remains** is (a) *embedding* the view in a widget another toolkit owns, which needs the `NSView*`/`Aspect_Drawable` constructors (2d), (b) the same on Windows (`WNT_Window`), and (c) event handling — nothing pumps the run loop from Python yet, so an interactive window is a separate design question. The pixel view of 8.10 would make `ToPixMap` zero-copy to numpy/Pillow. For reference, the original step was: rebuild OCCT with `USE_OPENGL=ON` (macOS `OpenGL.framework`; Linux `USE_XLIB=ON`, X11/GLX in the manylinux image; Windows wgl), generate `TKOpenGl` (98 headers, `OpenGl_GraphicDriver` is what `V3d_Viewer` needs) and `TKMeshVS`; then the window integration — `Aspect_NeutralWindow`/`Cocoa_Window`/`Xw_Window`/`WNT_Window` from a native handle held by a Python toolkit (Qt, wx, tkinter, GLFW), which is the raw-pointer/`Aspect_Drawable` gap of 2d — and offscreen rendering (`V3d_View::ToPixMap` → the pixel view of 8.10) for screenshots without a window. After DataExchange (2, "After Phase 2").

- **8.14** **Stream operators as Python methods.** 47 sites report `operator<<`/`operator>>` with a stream as *"iostream type"*: the C++ "print me" idiom `Standard_OStream& operator<<(Standard_OStream&, const T&)`, hidden friend or free, in `math` (25), `TDF`, `TCollection`, `Standard`, `FairCurve`, `BinTools`, `IntRes2d`, `VrmlData`, … plus one input operator, `VrmlData_Scene& operator<<(Standard_IStream&)`. Neither existing rule reaches them: R-FREE-OP does not apply because the stream is the first argument, so in Python terms the operator is not on the class, and R-STREAM-OUT fires on parameters of *bound* methods. For most classes this costs nothing — `Dump`/`Print`/`DumpJson` is bound next to it and returns `str` — but for `VrmlData_Scene` the pair *is* the whole text interface (2d, TKDEVRML). **Decided 2026-09-23, option (a):** the output operator becomes **`__str__`**, so `str(aVector)` gives OCCT's own rendering, and the one input operator gets a named method (`__lshift__` would read as a bit shift); a named `Print()` was rejected because it collides with the real `Print` on the 40 `Vrml_*` classes. To settle when implementing: what a class with both `Dump` and `operator<<` should render, and whether `__repr__` follows. **Deliberately deferred** (user: *"Put handling operator<< to the roadmap with option (a), I want to finish the remaining toolkits first"*) — `TKBinXCAF` and `TKXmlXCAF` close Phase 2 first, and the 2d rows carry the gap until then.

- **8.17** **The CI matrix — the last step.** Building the three wheels on every push and publishing them: a job per platform (macOS arm64, `manylinux_2_28` x86_64 in the container `deps/run-manylinux.sh` already uses, Windows x64 with MSVC), each running `make deps generate compile stubs test wheel` and uploading the repaired wheel, then a release job. **Blocked on a decision that is not technical: this repository has no remote and nothing has ever been pushed** (9), so there is nowhere for CI to run. Everything under it is ready — the three platforms build and test green from one `Makefile`, and 8.4 makes each one produce a self-contained wheel — which is why the user put this last (2026-09-24): *"Move 'CI matrix' to roadmap. This will be the last step"*. Decide with it: whether the OCCT build is a CI step (≈4 min wall, 46 min CPU on this hardware) or a cached artefact, since a cold `make deps` in every job would dominate the run.

### Decided

- **8.4** ~~**Wheel bundling**~~ — **done 2026-09-24, verified on all three platforms.** `make wheel` builds the wheel and repairs it (`raw_wheel` → `delocate` → `wheel`): macOS `delocate` 20 → 44 MB, Linux `auditwheel --plat manylinux_2_28_x86_64` 25 → 50 MB, Windows `delvewheel` 26 → 48 MB. Linux was checked on a real host (Ubuntu 22.04, glibc 2.35), not only in the image that built it. What each wheel bundles and what it leaves to the system is in Design.md 7, measured rather than planned. **Two failures paid for along the way, both now fixed in the build:** OCCT's dylibs name their siblings `@rpath/...` but carry no `LC_RPATH`, which is invisible at runtime and fatal to delocate (`deps/build-occt-macos.sh` adds `@loader_path`); and `uv build --no-build-isolation` silently picks its own interpreter without an explicit `--python`, failing with "No module named 'scikit_build_core'" although the venv has it. **Not verified:** the `@loader_path` step against a *clean* OCCT rebuild — it is proven correct and idempotent against the existing install only (a clean run costs ~4 min wall, 46 min CPU). The CI matrix that builds and publishes these wheels is roadmap **8.17**.
- **8.2** ~~**Generator, build and tests on Linux and Windows**~~ — **done 2026-09-24.** All three platforms generate, compile and pass the suite from the same source: **macOS 712 passed**, **Linux 709 passed / 3 skipped** (manylinux container, gcc 14, glibc 2.28, `USE_XLIB=ON`, under `xvfb-run`), **Windows 710 passed / 2 skipped** (MSVC 14.44), 45 modules each. Boxes: `gauss` (Windows 11, VS Build Tools 2022, MSVC 14.44, Windows SDK 10.0.19041, **no clang**) and `banach` (Ubuntu 22.04, 32 cores). The three libclang fixes below were the port; **the seven portability defects and the MSVC compile-time pathology are what the port actually found**, and they are in 9 "Seen with the platform port".
    - **Windows needed one line:** MSVC's STL refuses a clang older than itself (`yvals_core.h:899-917`, `STL1000`), and the pip wheel is libclang 18.1.1 — the newest published. A parse is not a compile, so `clang_args()` adds `-D_ALLOW_COMPILER_AND_STL_VERSION_MISMATCH` on Windows. libclang finds MSVC and the Windows SDK by itself.
    - **Linux needed a real fix in `configure_libclang()`:** it preferred the system libclang unconditionally, but Ubuntu's libclang 14 does not export `clang_CXXMethod_isDeleted`, which the pip bindings register on first use — and cindex accepts a library only once, so the choice cannot be undone. `_libclang_is_compatible()` now dlopens the candidate and checks for the symbols before committing.
    - **Python 3.12 is required and already declared** (`requires-python`); `emit.py` uses PEP 701 f-strings, so a 3.10 interpreter fails at import. `uv venv --python 3.12` is the answer, not a code change.
    - **The generated API is deliberately platform-identical now**, which was the open question. Where OCCT exports differently, the *skip* is applied on every platform rather than letting the generator drop members only where the symbol is missing (6, R-UNDEFINED and `overrides.toml` `[skip] constructors` / `max_params` / `[link] extra`). What remains platform-dependent is only what OCCT itself does differently: `Cocoa` is not built off macOS (`[platform]`), and `report.txt` differs because R-UNDEFINED compares against *this* platform's library.
    - **The container is the Linux build:** `deps/manylinux.Dockerfile` (PyPA manylinux_2_28 — AlmaLinux 8.10, glibc 2.28, gcc 14.2.1, cmake 4.4.3, auditwheel 6.8.2) plus `mesa-libGL/EGL-devel`, `libXext`, `libXmu`, `fontconfig-devel` and clang 21 for the generator; `deps/run-manylinux.sh` runs anything in it as the invoking user. The `.so` built there run unchanged on the host (glibc 2.28 → 2.35). **`USE_XLIB=ON`** follows OCCT's own default (`CMakeLists.txt:389` turns it off only for Apple and the no-Xlib platforms): with EGL the viewer never initialises (*"EGL display is unavailable"* even with a GPU). macOS and Windows keep it off because neither has X11 — the one flag on which the three OCCT builds deliberately differ.
    - ~~**Left for CI:** `deps/freetype-src` has no fetch script for the macOS build~~ — **closed 2026-09-25**: `deps/fetch-freetype-src.sh` and `deps/fetch-occt-src.sh` clone both at their pinned tags on every platform, and `make deps` now works on a bare checkout. What remains is that a Windows build must run in a **real session** — launched from an ssh command, process creation fails with `0xC0000142`; `nohup … &` under Git Bash does not survive either. `deps/build-occt-windows.sh` and `deps/build-occt-manylinux.sh` are the build scripts (the host-toolchain `deps/build-occt-linux.sh` was removed on 2026-09-24: the container is the Linux platform, so a second Linux build could only drift from it).

- **8.9** ~~**FreeImage**~~ — **decided 2026-09-22: no FreeImage.** Without it `Image_AlienPixMap` has one writer and no reader — `Save(path)` is always binary PPM (`P6`, RGB8, alpha dropped, per-pixel; `Image_AlienPixMap.cxx:1313-1328`), `Save(ostream)` and every `Load` return `false` (`:996-1010`, `:1523`); a Windows build without FreeImage uses WIC (`HAVE_WINCODEC`, `:16-18`) — **measured 2026-09-24: it is a real codec**, `Save` writes a PNG there rather than the PPM fallback, and its `InitTrash` rewrites RGB to BGR so `InitCopy` of an RGB source returns false ("pixel format conversion required"). OCCT decodes images only on the *display* path (`Image_Texture::ReadImage` from `XCAFPrs_Texture`, `Graphic3d_Texture*`, `OpenGl_View`, VR) and in `V3d_View::Dump`/`Image_Diff`; the glTF/OBJ/XCAF material path copies `Image_Texture` bytes and probes the format by magic number (`Image_Texture::ProbeImageFileFormat`), so textured glTF round-trips without a codec. build123d and CadQuery create no textures and take screenshots from browser viewers. Not kernel functionality: the third-party surface stays FreeType only (3.2); Pillow covers PNG/JPEG on the Python side (with roadmap 10 for zero-copy). Additive rebuild if textured `AIS` display is ever wanted. For the wheel, FreeImage would also have meant OCP's tail of 26 codec dylibs (`libpng`, `libtiff`, `libOpenEXR`, `libraw`, … in `cadquery_ocp_novtk-8.0.1.0.0`) unless built static from FreeImage's own tree.

- **8.12** ~~**A caster for `std::bitset<N>`**~~ — **done 2026-09-22 (R-BITSET, 6.3).** `ShapeProcess::OperationsFlags` (= `std::bitset<Operation::Last + 1>`, `ShapeProcess.hxx:74`) was the only `std::bitset` in scope and it cost nine members in two toolkits. A `std::bitset<N>` is now a Python `set` of the indices whose bit is set, which reads as the set of `ShapeProcess::Operation` enumerators because nanobind's arithmetic enums are `IntEnum`s. Bound since: `ShapeProcess::Perform(context, flags, range)` (TKShHealing), `XSAlgo_ShapeProcessor::ProcessShape`/`ReadProcessingData`, `XSControl_Reader::Set/GetShapeProcessFlags`, `Transfer_ActorOf{Transient,Finder}Process::Set/GetProcessingFlags` (TKXSBase). The two reports lost all nine lines; the `std` category is empty again outside TKernel.

- **8.13** ~~**Vendor RapidJSON**~~ — **done 2026-09-22** (user: "vendoring makes sense, to be prepared for the other OS"). `deps/fetch-rapidjson.sh` downloads the pinned tag `v1.1.0` and the upstream #718 patch Homebrew applies, verifies both sha256s (`bf7ced2970…bed98e`, `ce341a69d6…e0e1`), unpacks to `deps/rapidjson` and asserts the patched line is present; `deps/build-occt-macos.sh` points `CMAKE_PREFIX_PATH` and `3RDPARTY_RAPIDJSON_DIR` there instead of `/opt/homebrew/opt/rapidjson`. The patch is four lines in `include/rapidjson/document.h`: it removes a `GenericStringRef::operator=` that falls off the end without returning and declares it deleted. `diff -r` against the Homebrew headers shows **no difference**, so the switch changed the path and nothing else. Only the script is tracked, as for FreeType — the pinned tag plus the two hashes are the reproducibility, not a copy of the sources in git.

- **8.15** ~~**`TKDECascade`: the DE plugin for OCCT's own formats**~~ — **taken, generated 2026-09-23.** `DEBREP` and `DEXCAF`, 4 headers, 6 classes: `DE_Wrapper` now dispatches `.brep` and the OCAF documents by extension next to STEP, IGES and the mesh formats. The cost was measured before deciding, not estimated: **no further toolkit had to be generated** — `TKStd`, `TKStdL`, `TKTObj`, `TKBinTObj` and `TKXmlTObj` appear in its `EXTERNLIB` because its `.cxx` files use them, but in no header, so they are linked and not bound (`otool -L _TKDECascade.abi3.so` shows all five; `import nanoocp.TObj` raises `ModuleNotFoundError`, and a test asserts it). The price is 2.3 MB more OCCT dylib in the wheel. What it adds is dispatch, not capability: `BinTools.Write/Read` and `app.SaveAs`/`Open` were already bound.


## 9. Working state and how to continue (kept current for context resets)

### Seen with the parallel generation (2026-09-24)

- **Measure what the code actually asks for before designing around it.** The plan was to derive `known_elsewhere` from the tree, because 91.9 % of the 6 250 manifest classes follow their package name and the residue looked like the hard part. ### Seen with the platform port (2026-09-24)

Seven portability defects, none of which macOS alone could show. Every one is a case where two toolchains disagree about something the generator had treated as universal.

- **R-UNDEFINED ignored the destructor.** nanobind instantiates `wrap_destruct<T>` for *every* bound class, so a `~T()` the header only declares must be in the library. On Unix it always is (default visibility); on Windows only with `Standard_EXPORT`, which `Storage_Bucket` and `Storage_BucketOfPersistent` lack — the two `LNK2019` of the first Windows link. `Class.dtor_mangled` plus a class-level skip. Two traps inside it: libclang reports neither `is_definition()` nor `get_definition()` for `~X() override = default;`, so `is_default_method()` has to be asked separately (without it the rule ate `Message_PrinterToReport` and `Standard_Condition` on macOS); and **on Windows the destructor cannot be compared by mangled name at all** — libclang hands out the *vbase destructor* (`??_DBOPAlgo_Options@@QEAAXXZ`, a void-returning member) while the linker wants `??1BOPAlgo_Options@@UEAA@XZ`. Only the qualified name is common, so `symbols.destructor_defined()` prefix-matches `??1<name>@@`. Comparing the whole symbol skipped ~280 classes that link perfectly well.
- **`const` on a reference typedef.** OCCT writes `const typename Container::const_reference Value() const` (`NCollection_Iterator.hxx:86`), which is fine inside the template — [dcl.ref]/1 ignores the cv-qualifier — but our `static_cast` spells the type with the argument substituted, and there **gcc refuses it while clang accepts it**. libclang is no help: while the template is walked the type is `UNEXPOSED` with no canonical type and no declaration, so the spelling is the only handle and `_drop_ignored_const()` matches the two conventional reference typedef names.
- **`size_t` is not one type.** `NCollection_Vec3<size_t>::cwiseAbs` already had a `[skip]` entry under its LP64 spelling `unsigned long`; Windows is LLP64 and needed `unsigned long long` as a second entry for the same C++ type. (`unsigned char` instantiations are fine everywhere: they promote to `int`, so `abs(int)` is an exact match.)
- **The standard library resolves typedefs differently.** A `std::shared_ptr<std::ostream>` parameter defaulted to its own empty form was recognised by comparing the default expression with the type spelling. libstdc++ canonicalises the *type* to `std::basic_ostream<char, std::char_traits<char>>` while the default stays as written; libc++ keeps `std::ostream` on both sides. So the equality held on macOS and failed on Linux, and `RWPly_PlyWriterContext::Open` was skipped — the class bound but unusable, exactly what R-OPTIONAL-PTR exists to prevent. The check now only asks whether the default value-initialises an empty `shared_ptr`. The same divergence appears again in the report: `LDOM_OSStream`'s `std::ostream` base is reported as an unbound *class* by libc++ and as an uninstantiable *template base* by MSVC.
- **R-LINK misses a symbol reached through an included header.** The link line is derived from the toolkits owning the headers a module includes, which does not see a type used *inside* one of them. `_TKService/Font.cpp` includes `Font_BRepFont.hxx` for the deprecated alias, that header is really `StdPrs_BRepFont.hxx`, and `StdPrs_BRepFont` holds a `Geom2dConvert_CompCurveToBSplineCurve` **by value** (`:215`) whose constructor lives in TKGeomBase. Unix resolves it dynamically; a Windows import library must be named. Hence `overrides.toml [link] extra`.
- **`__hash__` is ours, not OCCT's.** The emitter writes a lambda calling `std::hash<T>`, which OCCT specialises inline as a forward to `T::HashCode()` — so where `HashCode` has no symbol the lambda does not link even though it needs none of its own. `__hash__` is now skipped when `HashCode` is, and the report says so.
- **OCCT exports per member, so a class can be unbindable in four different ways.** R-UNDEFINED skips the *member*; what fails is a symbol the compiler emits implicitly. (1) a non-pure virtual with no symbol — the vtable references it; (2) the destructor of a class held *by value* — the holder's implicit destructor needs it; (3) an **inline member whose body** calls an unexported one — the inline caller needs no symbol of its own, so it is bound happily and the call is emitted (`BRepGraph_UsagePath::operator==`→`IsEqual`, the `BRepMesh` functors' `operator()`→`process`, and two levels deep: `BRepMesh_CustomBaseMeshAlgo::generateMesh` → `BRepMesh_Delaun::ProcessConstraints` → `frontierAdjust`); (4) a signature too wide for the compiler — `StepData_EnumTool`'s 40-argument constructor hits MSVC `C1202`, which no flag raises (`/constexpr:depth2048` and `/constexpr:steps100000000` both tested; 37 parameters compile).
    - **Measured, not assumed:** on MSVC it is the **constructor** that stores the vptr, so it is the only thing that needs the vtable — binding the class, calling its methods through a pointer and `wrap_destruct<T>` all link. Hence `[skip] constructors`, which keeps a class bound and usable except for construction. But the full build then showed only **three of eight** candidates actually link that way; for the other five MSVC emits the vtable anyway (for `OpenGl_TriangleSet` explicitly through an `adjustor{32}` **thunk**, i.e. multiple inheritance; for the rest the symbol comes from data with no referencing function and **the cause is not established**). Those five stay class-level.
    - **The skips apply on every platform** so the API does not depend on who generated it. Cost: `BRepMesh_Delaun`'s four edge queries (no alternative; they never worked on Windows) and `BRepGraph_UsagePath.__eq__`. Everything else has a public equivalent that stays bound. **Open:** `BRepGraph_UsagePath` is hashable but not comparable on macOS, since `IsEqual`/`HashCode` are bound there and absent on Windows.

**MSVC compiles a binding registration function superlinearly.** `TKMath/math.cpp` — 531 `.def` calls in *one* function — took ~1677 s in the parallel build and **16 s** with nanobind's `NB_INLINE` as plain `inline` instead of `__forceinline`; `/Od` alone is 8 s, so it is the optimizer, not instantiation or code volume. ### Canonical regeneration and the re-homing guard

- Generation order matters the first time after deleting `src/cpp/manifest.json`: dependencies first (`TKernel`, then `TKMath`, …), because the manifest carries bound classes/instantiations across runs.
- Regenerating everything: `rm src/cpp/manifest.json` then all toolkits in dependency order. **Do that for any build whose output matters**: an on-demand instantiation (6c, and the NCollection instantiations of 6a) is bound by the first package that needs it, so an incremental run can leave it in a different package than a clean run does (`NCollection_Vec3<float>`: `Quantity` in a clean run, `BVH` after an incremental one); the clean order is canonical and reproducible byte for byte (`tests/test_generator.py` checks `TKG2d`).
- Since 2026-09-21 an incremental run **refuses** to bind an instantiation for the first time when a toolkit that is not being regenerated precedes the binding toolkit and could own it (`rehoming: … not regenerated`, exit 1, nothing written; `--allow-rehoming` overrides; only toolkits at or after the latest toolkit of the instantiation's argument types count).
- A fully canonical incremental run would need to re-parse the owner packages, i.e. the full 22 s parse of all 90 packages — the ritual plus the guard was chosen instead (decision log).
- A faster compile-only check without installing: `cmake --build build/dev` (configured with `-DPython_EXECUTABLE=$PWD/.venv/bin/python -DCMAKE_INSTALL_PREFIX=$PWD/build/stage`).

### Debugging a nanobind "Critical nanobind error" at import

Release builds hide the message.

- Build the Debug tree `build/debug`: `cmake -S . -B build/debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DPython_EXECUTABLE=$PWD/.venv/bin/python -DCMAKE_INSTALL_PREFIX=$PWD/build/stage-debug`, `cmake --build build/debug`, `cmake --install build/debug`, copy `src/nanoocp/*.py` into `build/stage-debug/nanoocp/`.
- Then `PYTHONPATH=build/stage-debug .venv/bin/python -S -c "import nanoocp._TKMath"` — `-S` is required because the editable-install `.pth` hook would otherwise load the Release module.
- For a C++ exception at init: `lldb --batch -o "break set -E c++" -o run -o "bt 12" -- .venv/bin/python -S -c "import nanoocp._TKernel"`.

### Recurring pitfalls

- safe-chain hides packages younger than 48 h from `uv`; the user overrides it themselves (nanobind is in the exclusions now).
- A `str.replace(old, new)` with an empty `old` inserts `new` between every character — it happened once to `parse.py` and was recovered exactly; use asserts on anchors.
- Partial regeneration of a single package is safe (toolkit module stays complete, manifest entries of the package are refreshed).
- Every new package tends to reveal one or two OCCT-specific idioms: the report printed by the generator (`- …: reason`, persisted as `src/cpp/<TK>/report.txt`; watch its `git diff` after a regeneration and the `misc` category) is the place to look, and the compiler/linker tells the rest.
